## 1. Executive Summary

The `/SCWM/ISU` transaction itself is **not** the bottleneck of the 24-hour load window.

The trace shows that the real cost per record comes from **custom Z/Y BAdIs, industry solution integrations, and configuration lookups** that fire on every goods movement generated by the Initial Stock Upload.

Estimated technical breakdown of the cost per record:

```
Custom Z/Y BAdIs (JVA + MIGO + Validation + PSA + Oil)   ████████████████████  40%
Syclo mobile framework (change pointers)                 ██████████░░░░░░░░░░  20%
CIF/APO sync + Central Finance                           ██████░░░░░░░░░░░░░░  12%
FI consistency checks + FINSC_* lookups                  █████░░░░░░░░░░░░░░░  10%
Oil & Gas + Regulatory (FERC)                            ████░░░░░░░░░░░░░░░░   8%
Material Ledger cost component split                     ███░░░░░░░░░░░░░░░░░   5%
Classification + Number range + RFC checks               ██░░░░░░░░░░░░░░░░░░   5%
```

Consequence: the biggest gain will come from **reducing what fires during the cutover window**, not from replacing `/SCWM/ISU`.

**Realistic reduction potential:** from ~24h to **~6–14h**, depending on how many optimization levels are applied.

## 2. Trace Findings — Top Offenders

### 2.1 Custom BAdIs and User Exits (Z / Y)

Custom classes appearing repeatedly across the trace, called per goods movement:

| Custom class | Purpose | Trace evidence |
|---|---|---|
| `ZCL_JVA_FI_DOC_DFTCO_IMP` | Default Cost Object for Joint Venture Accounting | 20+ hits on USOBX_C, ZI_WRAP_SETLEAF, ZI_JNTVNTRSUBSTITUTECOSTOBJECT |
| `ZCL_MIGO_BADI_HT_MODIFY` | Custom MIGO — Handling Type modification | USOBX_C, ZI_CONSTANTPARAMETERSF |
| `ZCL_DEFAULT_HT_GOODSMVT_CREATE` | Custom Goods Movement default | UST12, ZI_CONSTANTPARAMETERSF, I_PRODUCTPLANTBASIC |
| `ZCL_OIL_MATERIAL_PROCESS` | Oil & Gas material processing | USOBX_C, I_PRODUCT |
| `YCL_MB_MIGO_BADI_LOGIC` | Extra MIGO logic | YI_ZERO_PRICE_MAINT, YI_PLANT_NODETYPE_RESTRICTION |
| `YCL_MB_DOCUMENT_BADI` | Document-level BAdI | ZI_CONSTANTPARAMETERSF, IPRODUCT |
| `ZCL_VALIDATE_MATDOC` | Material document validation | IPRODUCT |
| `ZCL_EXP_INV_OPEN_BIN_BTE` | Business Transaction Event (BTE) — open bin | ZI_CONSTANTPARAMETERSF |
| `ZCL_ACC_DOC_CREATE_ACKNOW` | Accounting document acknowledgment | ZI_CONSTANTPARAMETERSF |
| `ZCL_MB_CHECK_LINE_LOGIC` | Line check | ZI_USR05 |
| `ZCL_DERIVE_PSA_MAIN` | PSA derivation | ZDB_PSA_CCODE |

Each of these performs multiple SELECTs per invocation (USOBX_C authorization checks, custom Z configuration tables, `I_PRODUCT` / `IPRODUCT` CDS views). Aggregated, this layer represents the largest single portion of the runtime.

### 2.10 Number ranges not buffered

- `NRIV` accessed via `SAPLSNR3` (non-buffered path)
- Prepare / Open / Fetch cycles visible per document
- Should be running through the buffered path (`SAPLSNR1`) or with buffering enabled at SNRO level

### 2.11 RFC destination re-check per call

Tables read repeatedly via `CL_DEST_RFC` / `CL_DEST_ROOT`:
`RFCDES`, `RFCATTRIB`, `RFCDESSECU`, `RFCDOC`, `RFCCHECK`, `RFCCBWHITELIST`

### 2.12 Commit is not the bottleneck

Only **one** `Commit Work` event appears in the traced window (from `/SCWM/CL_MIG_STOCK`).
Commit frequency is not the driver — the per-record customization and integration load is.

## 3. Recommendations — By Impact and Effort

### Level 1 — Configuration Quick Wins (days, immediate gain)

| # | Action | Where | Expected gain |
|---|---|---|---:|
| 1 | Deactivate Syclo framework during cutover | Syclo customizing / IMG | **-15 to -25%** |
| 2 | Deactivate Z/Y BAdIs (filter by migration user or IMG toggle) | SE18 / SE19 / IMG | **-25 to -40%** |
| 3 | Suspend CIF outbound to APO during load | CFC9 / CIF outbound queues | **-8 to -12%** |
| 4 | Suspend CFIN replication for the logical client during load | CFIN configuration / RFC destination | **-3 to -6%** |
| 5 | Enable buffering on `MB` and related number ranges | SNRO — turn off "no buffering" | **-2 to -5%** |
| 6 | Verify buffering on FI config tables (`FINSC_*`, `TCVPROF`, `TCVPROFT`) | SE13 (where technically allowed) | **-2 to -4%** |

**Realistic combined gain from Level 1: ~40–60%** → **24h → ~10–14h**, using configuration only, no development.

### Level 2 — Design Change (weeks, larger gain)

| # | Action | Gain vs. 24h |
|---|---|---:|
| 7 | Replace `/SCWM/ISU` with a Z program calling `/SCWM/API_PHYSTOCK_CREATE` directly, with package size 100 + parallelism 5 | **~65–75%** (24h → ~6–8h) |
| 8 | Migrate to Migration Cockpit object "Warehouse stock (EWM)" | ~40–50% |

### Level 3 — Scope Reduction (days, potentially highest gain of all)

| # | Action | Gain vs. 24h |
|---|---|---:|
| 9 | Confirm whether all 28,687 records really need to be migrated (residual balances / neutral positions can be dropped) | 10–100% depending on scope |
| 10 | Split the load by warehouse (partition per storage location / storage type) and run in parallel | additional -40 to -60% |

## 4. What Will *Not* Help Significantly

Based on the trace evidence:

- ❌ **Hardware upgrade** — the bottleneck is ABAP logic, not I/O.
- ❌ **More work processes alone** — the serialization is inside each document.
- ❌ **Individual SELECT tuning** — every single SELECT is fast; the cost comes from the **quantity** of them.
- ❌ **HANA hints or new indexes** — the hot tables are already buffered or small.

## 5. Correction to the Original Migration Report

The original migration report (`Migration-BAPI-Report.md`, section **3.1 Inventory (EWM)**) assumed a maximum gain of **0–20%** because no direct BAPI exists for `/SCWM/ISU`.

The trace analysis proves this assumption is **too conservative**. A **60–75% reduction is achievable**, but through a different path:

- Not by replacing the API
- But by **eliminating the customization and integration layers** that fire per record during the cutover window

Most of the gain is **operational and cutover-configuration driven**, not development driven.
